PAPER REPORT
Title: Flexible Zero Trust Architecture for the Cybersecurity of Industrial IoT Infrastructures
Authors: Claudio Zanasi, Silvio Russo, Michele Colajanni
Journal: Ad Hoc Networks, Vol. 156 (2024), Article 103414
Publisher: Elsevier

===================================================================
1. ABSTRACT
===================================================================
Growing digitalization of industrial systems and cloud adoption create
significant challenges in securing heterogeneous Industrial Internet of
Things (IIoT) infrastructures, which require hard real-time operation,
high reliability, and decentralized decision-making — requirements not met
by existing uniform/centralized cybersecurity solutions. The authors
present a novel security architecture based on network micro-segmentation
with two main components: (1) a software-defined network (SDN) providing
a unified abstraction layer for policy enforcement, and (2) a centralized
security management layer simplifying policy execution. A prototype
demonstrates that a peer-to-peer SDN with asynchronous policy distribution
guarantees resiliency to individual failures while enabling fully
decentralized operation alongside centralized management of topology and
security policy.

===================================================================
2. INTRODUCTION
===================================================================
The proliferation of cyber-physical systems, cloud integration with
industrial plants, remote work, and BYOD has transformed industrial
landscapes, making traditional VPN-based perimeter security and implicit
trust in internally connected devices obsolete. The Zero Trust security
model is emerging as the preferred approach for protecting critical
infrastructure (power grids, transportation, water treatment) because in
ZT, no architectural element implicitly trusts another — every interacting
component is continuously identified and authorized.

The authors identify micro-segmentation as the most promising ZT technique
for heterogeneous industrial IoT environments: it enables granular control
and isolation of network segments, enhances visibility via strict
communication rules, facilitates breach containment, and adds attacker
complexity (must traverse multiple segments). However, micro-segmentation
is theoretically valid but effort-intensive to implement/maintain,
especially given the sheer volume of policies required in large,
heterogeneous industrial networks, and the need for continuous policy
updates as the network evolves.

Contributions:
1. A novel ZTA design optimized for heterogeneous industrial environments,
   extensible to cloud and IoT solutions.
2. A network management strategy addressing micro-segmentation's main
   challenge — efficient policy management.
3. Validation through a prototype emulating a realistic environment.

3. BACKGROUND / LITERATURE REVIEW
===================================================================
Related Work reviewed by the authors:
- Li et al.: identifies key industrial-sector challenges (scalability,
  security) and 5G-IoT network management issues, but offers only
  theoretical analysis without addressing real design/implementation
  challenges.
- [15] (unnamed authors, microservice ZT): proposes zero-trust security
  for micro-service architectures but relies on questionable assumptions
  (trustworthy infrastructure provider, vulnerability-free provider
  infrastructure) that undermine ZT's foundations; fine-grained access
  policies are unsuitable for large-scale, frequently-changing
  environments.
- Paper [20]: explores SDN's role in supporting ZT in cloud computing,
  discussing strong authentication, access control, securing inter-cloud
  traffic, and managing multiple providers; emphasizes micro-segmentation
  but offers only theoretical analysis, not addressing real-world
  deployment issues.
- Paper [10]: describes micro-segmentation-via-SDN benefits but also
  challenges: substantial network modifications and single-point-of-
  failure risk of a central SDN controller — this paper is the primary one
  this work addresses.
- SDN-related papers [21-24]: discuss the centralized vs. distributed SDN
  controller debate; centralized architectures favor management but limit
  scalability/resilience since disruptions or request overload can
  jeopardize the single central controller (a single point of
  vulnerability).
- Distributed SDN controller papers [30-32]: enhance resilience/
  scalability but complicate management/configuration synchronization.

Gap: prior work either uses centralized SDN controllers (single point of
failure) or purely theoretical analyses without addressing practical
deployment. This paper proposes a hybrid: scalability/robustness of
distributed controllers combined with the simplicity of centralized
configuration.

4. OBJECTIVES / DESIGN PRINCIPLES
===================================================================
The paper's IIoT security architecture is guided by four principles:
1. Resource centric: security perimeter concepts are obsolete with 5G/
   wireless connectivity; authentication must focus on individual
   resources, not network boundaries.
2. Decentralization: avoid single points of failure that could cause
   cascading failures with safety implications in critical infrastructure.
3. Reduced overhead: hard real-time industrial constraints require minimal
   performance impact, especially as micro-segmentation granularity
   increases the number of enforced security rules.
4. Backward compatibility: industrial systems change more slowly than pure
   software systems (legacy technologies, long equipment lifetimes), so
   the security system must minimize disruptive/breaking changes.

--- 5.2 Methods (Architecture Description) ---
The proposed architecture modifies the NIST ZTA logical model by
decentralizing the PDP and PEP: each resource hosts its own local PDP/PEP
pair, while a central management system maintains the global security
configuration in a policy repository. A configuration service computes
the minimal local configuration needed per PDP (only policies relevant to
that specific resource) and securely distributes it via authenticated
channels. A monitoring service continuously collects data from PDPs for
real-time network status assessment; if discrepancies from the global
configuration are found, the central system recomputes and redistributes
corrected local configurations — ensuring policy enforcement continues
even if central management is temporarily unavailable.

PEP is moved to computing resources via smart network interfaces
implementing an overlay SDN on top of existing infrastructure (IP-based),
providing a consistent abstraction layer requiring only IP pointer/DNS
updates to integrate with existing services. Resource authentication uses
digital certificates at the smart interface level (mutual authentication),
embedding security metadata (access privileges) directly in the
certificate — enabling each resource to autonomously accept/reject
connections without querying a central authority during the connection
handshake. This makes every IIoT connection end-to-end encrypted.

The two primary components:
- SDN: handles ordinary network operation (peer discovery, DNS, smart
  routing); designed to be decentralized/peer-to-peer to enhance
  resiliency and scalability.
- Centralized management system: monitors topology/resource state,
  defines/updates network configuration and security policies, issues/
  distributes digital certificates, and manages security metadata
  encoding access privileges.

--- 5.3 Implementation Details ---
Prototype built on the open-source Nebula software-defined overlay network
(encrypted point-to-point channels, high-level security groups embedded
in certificates for firewall rule enforcement). The authors developed:
- A configuration management system (Dhall-language library) for
  centralized network/security-policy definition with structural
  validation at type-checking time.
- A certificate distribution service adapting the EST (Enrollment over
  Secure Transport) protocol, comprising three components:
  1. NEST (Nebula Enrolling over Secure Transport) service: reverse proxy,
     the only publicly-exposed component, forwarding requests to internal
     CA and Configuration services.
  2. Certificate Authority (CA) service: manages digital certificates
     (custom, non-X.509-compliant Nebula certs); stores root cert/master
     key; deployed in an isolated network accessible only via the NEST
     service's REST API; supports certificate blacklisting (no
     traditional CRL support in Nebula).
  3. Configuration service: manages the centralized policy repository;
     provides an API for initial and updated client configuration.
- NEST client: a Go-language daemon deployed alongside Nebula on each
  resource; handles enrollment, config updates, and certificate renewal;
  authenticates to NEST service via an HMAC-based secret token (derived
  from client hostname + 256-bit symmetric key), limiting compromise
  blast radius to a single resource's identity.

--- 5.4 System Requirements (Testbed Infrastructure) ---
- Cloud platform: Microsoft Azure (for NEST services and Linux clients);
  personal devices for other components (Raspberry Pi4b for Lighthouse,
  real Windows PC, and a smartphone for Android client).
- VM sizing: most Azure VMs provisioned as low-resource "B1ls" (512MB RAM,
  1 vCPU) to highlight minimal system overhead; Configuration Management
  service provisioned as "B2s" (2 vCPUs, 4GB RAM).
- Network policy: all virtual networks deny incoming traffic by default,
  except UDP port 4242 (Nebula's default communication port) and NEST's
  port 8080 (enrollment/re-enrollment, exposed to Internet).
- Performance test setup: two virtual machines (one hosting Lighthouse,
  one hosting a Web server) plus two Kubernetes clusters (6 vCPU, 16GB RAM
  per node) generating HTTP client load across multiple availability
  zones (East US, East US 2, Japan East).
- Load test: each client sends an HTTP GET every 250ms for 15 minutes;
  twelve tests run for client counts from 50 to 300 (steps of 50), equally
  split across two data centers.

6. RESULTS
===================================================================
--- 6.1 Resource Overhead (Table 1) ---
| RAM  | CPU    | Connections | CPU Usage | RAM Usage |
| 1 GB | 1 vCPU | 50          | 18.4%     | 1.5%      |
| 4 GB | 2 vCPU | 200         | 12.8%     | <1%       |
| 8 GB | 2 vCPU | >300        | 15.1%     | <1%       |
Even a 1GB/1vCPU web server handles 50+ concurrent connections easily;
Nebula's overhead remains remarkably small even as hardware scales up,
demonstrating efficiency across diverse hardware configurations.

--- 6.2 Response Time Comparisons (Figs. 12-14) ---
At 50 clients, both Nebula-overlay and baseline architectures perform
similarly (~0.3-0.4s response time). At 150 and especially 300 clients,
the Nebula-based (proposed) architecture shows markedly lower response
times and failure rates than the baseline, which exhibits multiple
horizontal "bands" caused by TCP's congestion-control exponential
back-off misclassifying increased latency under stress. The proposed
architecture's TCP-over-UDP mode continues transmitting despite server
stress, avoiding this degradation — a significant advantage for
industrial/real-time IoT applications.

--- 6.3 Scalability Analysis ---
- No performance degradation observed even on resource-constrained
  devices.
- The peer-to-peer SDN architecture scales efficiently by distributing
  policy-enforcement workload, which is especially effective for
  industrial networks where most communication stays local.
- NEST Service and Certificate Authority can both be horizontally scaled
  (enrollment/re-enrollment flows are logically independent/stateless).
- The Configuration Service (maintaining global network state) is
  identified as the architecture's potential bottleneck, since it must be
  queried on every enrollment/re-enrollment flow — though its read-heavy,
  cache-friendly access pattern (given the relatively low rate of change
  for critical security configs, and use of abstract security tags)
  allows significant optimization potential.
- Re-enrollment introduces only a small localized latency spike (~100ms
  on Linux; 3-4s on Windows due to Nebula's Windows interface
  optimization limitations) without disrupting ongoing operations
  (enabled by TCP-over-UDP restart capability).

7. DISCUSSION (Trade-offs)
===================================================================
The architecture facilitates IT/OT convergence by providing a unified
security abstraction at the network layer that protects both IT and OT
components without requiring hardware modification to legacy OT
equipment. Devices lacking native Nebula support can be integrated via a
"Nebula unsafe mode" NAT gateway device (with the caveat that
device-to-gateway traffic is initially unencrypted — mitigated by adding
a low-power NAT device per unsupported resource).

Key trade-offs versus centralized PDP designs:
- Traditional centralized PDPs require a round-trip per authorization
  request (even within the same plant), incompatible with real-time
  requirements and physical distance constraints — this design uses
  point-to-point connections to minimize latency.
- Centralized PDPs create a single point of failure that could disrupt
  the entire network; this distributed design enhances resiliency and
  scalability by distributing policy enforcement.
- Dynamic topology changes are not instantaneous — configuration updates
  must propagate to all nodes, requiring continuous monitoring to confirm
  completion; remediation of a compromised resource may take longer than
  in a centralized system, though micro-segmentation limits the "blast
  radius" of any breach and raises the bar against privilege escalation/
  lateral movement.
- Because all connections are peer-to-peer and end-to-end encrypted,
  traditional centralized traffic-capture-based security monitoring is no
  longer possible; instead, each PDP acts as a dual-role
  enforcement-point/reporting-node, forwarding policy-violation
  information to the central monitoring service for global visibility.
  Mutual authentication via digital certificates significantly raises the
  difficulty of spoofing attacks, making policy violations a
  high-signal-to-noise indicator of malicious activity.

===================================================================
8. FUTURE DIRECTIONS
===================================================================
The authors' stated future work: enhance the monitoring service (which
currently only detects disparities between the defined and actual network
topology/status) by adding an analytical engine that uses AI to proactively
identify malicious activities from resource-generated security
information — aiming to further increase resilience against malicious
actors.

===================================================================
9. CONCLUSION
===================================================================
The paper proposes a novel security architecture using software-defined
networks to implement a micro-segmentation Zero Trust Architecture
specifically for industrial systems and heterogeneous environments,
addressing existing security approaches' limitations via a flexible
configuration management system deployable across multi-cloud/hybrid-cloud
setups. Leveraging the Nebula overlay SDN plus a custom configuration
management system (automating certificate/configuration generation and
distribution) and a portable multi-OS/multi-architecture client, the
authors demonstrate a comprehensive solution securing IIoT systems,
diverse networks, and cloud platforms without modifying end applications
— only IP/DNS pointer changes are needed, paving the way to extend Zero
Trust principles to IIoT environments.

===================================================================
RELEVANCE TO "ZTA FOR WSN" TOPIC
===================================================================
This paper is highly relevant to ZTA for WSN: its resource-centric,
decentralized, low-overhead, backward-compatible design principles were
explicitly created for resource-constrained, heterogeneous, real-time IoT
devices — the same category WSN nodes fall into. The measured minimal
overhead (as low as ~1.5% RAM, ~18% CPU on a 1GB/1vCPU device) and the
peer-to-peer, certificate-based mutual-authentication micro-segmentation
approach (rather than a centralized PDP requiring round-trips) directly
addresses the latency and resource constraints that would be critical
concerns in applying Zero Trust to Wireless Sensor Networks.
