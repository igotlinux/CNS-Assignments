PAPER REPORT
Title: A Critical Analysis of Zero Trust Architecture (ZTA)
Authors: Eduardo B. Fernandez, Andrei Brazhuk
Journal: Computer Standards & Interfaces, Vol. 89 (2024), Article 103832
Publisher: Elsevier

===================================================================
1. ABSTRACT
===================================================================
Zero Trust (ZT) is a heavily promoted approach for building secure systems
that rejects trusting any resource-access request by default. The authors
use security patterns (a method previously used to design/evaluate secure
architectures) to critically analyze ZT's claims. They argue that industry
publications on ZTA are vague about technical details, often ignore past
security knowledge, and rarely report actual implementation experience.
The paper asks: Is ZTA the ideal architecture for building secure systems?
To answer, they decompose ZTA into its pattern structure, sketch a
preliminary reference architecture built from an aggregation of security
patterns, analyze ZTA's threats, and propose directions for future
research.

===================================================================
2. INTRODUCTION
===================================================================
ZTA is promoted as significantly increasing organizational security, driven
by the complexity/heterogeneity of modern IT (multiple internal/external
networks, cloud, IoT, cyber-physical systems, BYOD, Work From Home). This
fragmentation has enlarged the attack surface amid increasingly
sophisticated and frequent attacks.

The authors note ZT is a strategy/philosophy, not a specific architecture,
making implementation unclear; few actual implementation reports exist,
and vendor white papers are largely high-level. ZT's foundational concept
is the application of security principles from Saltzer & Schroeder's
classic paper, to which ZT adds "trust no one." The problem: principles are
abstract and don't provide concrete implementation guidance; a systematic
secure development methodology, not just added mechanisms, is needed for
genuinely secure systems.

Contributions:
1. Description of the evolution of major ZTA industry proposals,
   highlighting features/principles used, showing diverse interpretations.
2. Discussion of ZTA's relation to classical security theory, showing
   ZT's basic concepts predate the "Zero Trust" label.
3. Enumeration of architectural security mechanisms in ZTA as security
   patterns.
4. A preliminary Security Reference Architecture (SRA), more precise than
   existing block-diagram-only descriptions.
5. Preliminary answers to five key research questions:
   Q1. Does ZT apply many unnecessary checks?
   Q2. Does ZT introduce an intolerable overhead?
   Q3. Is ZT implementable for most institutions?
   Q4. Does ZT control more, fewer, or similar threats vs. other approaches?
   Q5. Does ZT produce a huge number of policies?

3. BACKGROUND
===================================================================
--- 3.1 Principles ---
Saltzer & Schroeder's classic principles (applied in most ZT systems):
Closed system, Least privilege (need to know), Complete mediation, Open
design, Economy of mechanism, Minimal trust, Separation of privilege,
Least common mechanism, Safe defaults.

Later-proposed principles also relevant to ZT: Highest level (security
constraints defined at application layer, propagated down), Holistic
security, Ease of use/transparency, Information hiding & encapsulation,
Defense in depth, Compartmentalization, Submarine principle (accept losing
some units, protect essential ones), Compromise recording.
Specific ZTAs generally adopt at least: closed systems, least privilege,
and complete mediation.

--- 3.2 Security Patterns and Reference Architectures ---
A pattern is a reusable, templated solution to a recurrent problem,
containing context, problem, solution (UML diagrams), implementation
guidance, known uses, consequences, and related patterns. Security
patterns additionally list threats handled and corresponding defenses.
Over 200 security patterns exist covering Access Control, Network
Security, Web Services Security, etc.

A Reference Architecture (RA) is a generic, abstract, implementation-free
architecture built from one or more domains; it can be constructed using
patterns. Adding security patterns to control identified threats in an RA
produces a Security Reference Architecture (SRA).

4. ZTAs IN INDUSTRY (Literature Review)
===================================================================
The paper surveys major industry ZTA proposals:
- Forrester's network-driven ZT architecture: uses most Saltzer principles
  (closed system, fail-safe defaults, least privilege, separation of
  privilege, network isolation, complete mediation, compromise recording,
  continuous protection, defense-in-depth); network-centric, emphasizes
  network segmentation and centralized management.
- Zero Trust Network Access (ZTNA): variant checking (user, device) tuple
  credentials, creating an encrypted tunnel and logging/monitoring;
  integrates with SD-WAN, SASE, cloud security.
- Zero Trust Extended (ZTX): extends ZT to data, network, people,
  workloads, devices; Forrester's framework covers strategy, capability,
  technology, features, but lacks implementation detail.
- Google BeyondCorp: application-style ZTA removing the need for a
  privileged perimeter; built from access proxy, SSO, RADIUS
  authentication; an Access Control Engine uses dynamically evaluated
  trust levels based on user/device databases.
- NIST ZTA (Fig. 1 in paper): authentication/authorization follow dynamic
  policies; access is only granted for the duration of a session.
  Components: Policy Enforcement Point (PEP), Policy Decision Point (PDP)
  comprising Policy Engine (final decision) and Policy Administrator
  (controls communication). Extra features: Continuous Diagnostics and
  Mitigation (CDM), industry compliance, threat intelligence, activity
  logs, PKI, ID management, SIEM. Uses a "trust algorithm" fed by policy
  database, subject attributes/roles, behavior history, and threat
  intelligence.
- Qi Anxin (Gartner-referenced) framework: identity-based schema,
  continuous trust evaluation, resource secure access, adaptive access
  control; defines access objects/subjects as dynamic combinations of
  (user, application, device); uses continuous trust evaluation with all
  traffic TLS-encrypted.
- Microsoft ZT implementation: full-or-no access model (no granular access
  types); authentication based on location/device/user/risk via Active
  Directory; specialized IoT segments.
- Google BeyondCorp device database: tracks managed devices via
  certificates; only managed devices access corporate applications.
- NIST NCCoE and Cloudflare: working on standards-based, interoperable
  ZT implementation documentation.

5. METHODOLOGY / PATTERN ANALYSIS
===================================================================
--- 5.1 Authorization and Identity Models (patterns) ---
- Access matrix model: tuple (s, o, t, p, f) — subject, object, access
  type, predicate (condition), copy flag.
- RBAC: rights assigned to roles, not individuals.
- ABAC: subjects/objects described by attribute sets (location, rank,
  role, context) — finer granularity than RBAC.
- XACML (eXtensible Access Control Markup Language): general access
  control language; defines Policies via a Composite pattern (PolicySet ->
  Policy -> Rule -> Target). Includes:
  - XACML Authorization pattern (defines policies/rules/PAP)
  - XACML Access Control Evaluation pattern (Fig. 3): separates PDP from
    Access Response decision; Policy Information Point (PIP) supplies
    data; Context Handler converts formats.
  Noted as too complex for widespread industrial use; NIST's PDP merges
  PDP/PAP/PIP concepts and typically uses simpler RBAC/ABAC instead.
- Application Firewall pattern (Fig. 2): includes Policy Authorization
  Point (PAP, containing Identity Base + Policy Base), Policy Enforcement
  Point (PEP), and Content Inspector (verifies well-formed
  requests/signatures) — this structure underlies most ZTA proposals.
- Reference Monitor / Reified Reference Monitor pattern: intercepts
  resource access attempts and decides total/partial/denied access.
- Identity patterns: Identity Provider pattern (manages identities within
  a security domain), Circle of Trust pattern (Fig. 4: federation of
  mutually trusting Service Providers), Identity Federation pattern
  (dynamically created cross-federation identity).

--- 5.2 Network Models (patterns) ---
- Network Segmentation pattern: separates sections with different
  protection requirements.
- Micro-segmentation: creates protected segments of arbitrary size behind
  gateways, implemented via firewalls, activity monitoring, access
  control, content control, IDS/IPS, cryptography. Forrester's approach
  uses a Segmentation Gateway (SG) to create Microcore and Perimeter
  (MCAP) segments plus a Data Acquisition Network (DAN) for centralized
  log/event capture.
- Software Defined Perimeter (SDP): controls resource access by identity
  with least-privilege policy; uses Single Packet Authorization (SPA, a
  port-knocking variant) and TLS.
- Software Defined Network (SDN): separates control plane (software) from
  data plane (standard hardware); several papers propose combining SDN +
  SDP for scalable ZTA.
- Cryptography: PKI is commonly referenced but symmetric encryption for
  database protection is often overlooked; patterns for symmetric/
  asymmetric crypto and digital signatures exist but performance studies
  in ZT networks are lacking.

--- 5.3 Patterns and SRA in ZTA ---
Fig. 5 (Patterns used in ZTA) shows relationships among patterns:
Identity -> Authenticator (identify); SSO and Multifactor are types of
Authenticator; Authenticator -> Authorizer (authenticate); UCON -> usage of
Authorizer; XACML -> mechanism for Authorizer; Authorizer defines rights
for Segmentation, CASB, and Sandbox patterns; RBAC/ABAC are ways to
implement Authorizer; XACML composed of Rule def + Evaluation; Sec logger
performs log/audit on Evaluation.

Additional patterns discussed:
- Security Layers pattern: separates architectural layers (application,
  OS/database, middleware, networking, hardware) — the paper notes ZT
  work typically only considers control/data planes, which is
  insufficient to characterize threat distribution.
- Controlled Execution Domain (Sandbox) pattern: defines a secure
  execution environment specifying allowed resources/access types for a
  process.
- Cloud Access Security Broker (CASB) pattern: controls user access to
  cloud applications via an authentication service and policy evaluation.

--- 5.4 Preliminary Security Reference Architecture (Fig. 6) ---
Built on the NIST ZTA model but more precise: classes include PDP (holding
Data Policy), Policy Engine (PE) and Policy Administrator (PA) (linked to
Security Logger), a Decision class, Subject and Enterprise Resource linked
via PEP (Policy Enforcement Point), Resource Request, Communication Path
(abstract pattern for SDN/TLS/other protocols), and PKI. This maps
directly onto the Reified Reference Monitor and Application Firewall
patterns discussed earlier.

--- 5.5 Threats and Governance in ZTA ---
Combining NIST's and Ferretti et al.'s threat findings, six threat
categories are summarized:
1. Subversion of the decision process (attacks on PE/PA/control plane) ->
   disruption/unauthorized access.
2. Attacks to Infrastructure Certification Authority (introducing fake
   PE/PA components).
3. Denial of service (blocking interfaces that receive requests).
4. Unauthorized access to security information (data policies, identity
   info, trust repositories, device inventories).
5. Coercion of automated functions (e.g., trust calculations).
6. Device Certification Authority compromise (DCA signing key theft).

The authors note this is not a fully systematic threat enumeration (which
would require considering all use cases); governance aspects (role
assignment/definition/management, attribute definition, UCON, compliance
with health/financial/government regulations) are also identified as
under-addressed in ZTA literature.

6. RESULTS (Answers to Research Questions, Section 5)
===================================================================
Q1. Does ZTA apply many unnecessary checks? Possibly yes for some data
(e.g., publicly accessible product descriptions); per the "submarine
principle," not everything needs equal protection. Unnecessary checks add
performance overhead, though this cannot be precisely quantified without
statistical data; overhead is application-dependent.

Q2. Does ZTA introduce an intolerable overhead? RBAC/ABAC overhead is
generally acceptable since many systems already use these models. However,
dynamic/trust-based access control (recomputing trust per request) is
poorly defined in existing architectures and could add significant
latency; no ZTA overhead figures have been published to date.

Q3. Is ZTA implementable for most institutions? Feasible with vendor
support via gradual, business-driven implementation and maturity models,
though intermediate implementation stages may be less secure than needed;
patterns can provide a systematic roadmap.

Q4. Can ZTA control more/fewer/similar threats vs. other approaches? The
hardest question. ZT concentrates on controlling the attack surface but
does not address threats arising from application-level interactions
(e.g., CSRF/XSS in applications requiring user input) or address all
architectural layers systematically; database-level content-based access
control cannot be enforced purely via micro-segmentation.

Q5. Does ZT produce a huge number of policies? Yes — as flagged by Bertino,
micro-segmentation-based ZTA can produce an enormous number of segments/
policies. The authors argue microsegmentation is fundamentally limited: it
is a multilevel model that separates data by sensitivity but cannot
enforce fine-grained access-type control within a segment, and dividing
segments further adds gateway complexity/overhead. They recommend a more
logical approach: application-centric access control tied to data
semantics, developed via a systematic secure development methodology.

7. FUTURE DIRECTIONS (Section 6)
===================================================================
Identified research directions include:
- Survey and compare commercial ZT offerings in a comprehensive table.
- Precisely define "trust," how to apply it in access decisions, and its
  overhead.
- Study efficient use of NIST-model inputs (SIEM, compliance, data access
  policies) in access decisions.
- Build a complete Security Reference Architecture for ZT (this paper only
  provides a partial model).
- Build and measure a realistic ZTA prototype (security overhead, degree
  of security) rather than a "toy system."
- Write formal security patterns for SDP and SDN.
- Extend abstract patterns to specific application contexts (e.g.,
  financial vs. gaming applications) to build application-oriented ZT RAs.
- Study SDN + SDP combination for ZT implementation.
- Study database protection (authentication + authorization + cryptography)
  within a ZT environment.
- Conduct performance studies of cryptography use in ZT networks; propose
  intelligent (not brute-force) cryptographic approaches.
- Perform a systematic threat enumeration for ZTA components using
  use-case-driven methodology.
- Develop governance models for ZTAs (UCON, role engineering, alignment
  with governance frameworks).
- Collect real-system data to more precisely answer Q1-Q5.
- Find threats that cannot be handled by pure ZTA (partially addressed
  here in Section 5/Q4).
- Combine a secure systems development methodology with a ZT approach.

===================================================================
8. CONCLUSION
===================================================================
The authors analyzed architectural and implementation aspects of ZTA using
security patterns to connect ZTA to classical security theory, answering
five foundational questions about ZT's value and limitations. They found
current ZTA literature under-discusses performance, threats, and
governance, and that there are very few reports of real implementation
experience with actual performance/security measurements. As far as the
authors know, this is the first work to analyze ZT from a classical
security-theory viewpoint, decompose ZTAs into patterns, and propose a
pattern-based reference architecture for ZT. Future work will complete the
preliminary Security Reference Architecture, requiring new and adapted
security patterns combined into a full RA, followed by systematic threat
enumeration and defense mapping.

===================================================================
RELEVANCE TO "ZTA FOR WSN" TOPIC
===================================================================
This paper's pattern-based decomposition of ZTA (Application Firewall,
Reference Monitor, Identity Provider, Circle of Trust, Micro-segmentation,
SDP/SDN patterns) and its critical questions about overhead, policy
explosion, and threat coverage are directly relevant when designing ZTA
for WSNs, where resource constraints make "unnecessary checks" (Q1) and
"intolerable overhead" (Q2) especially critical concerns, and where
micro-segmentation at the sensor/node level must be carefully balanced
against the paper's warning about policy proliferation (Q5).
